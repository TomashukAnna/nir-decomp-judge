# Эмбеддинги требований и ТЗ WebGen-Bench

Материалы получены от руководителя 22 ноября 2026 года. Исходные файлы перенесены
без изменения содержимого; SHA-256, размеры и результат проверки записаны в
[run.json](run.json). Этот MLflow run относится к нашему аудиту файлов и поиску
соседей. Run ID исходного расчёта эмбеддингов руководителем не предоставлен.

## Где лежат файлы

Все три исходника находятся локально в
`data/requirement-bank/embeddings/received-2026-11-22/`:

- [catalog-webgen-maps.html](../../../data/requirement-bank/embeddings/received-2026-11-22/catalog-webgen-maps.html)
  — интерактивные карты; открыть файл в браузере. Внешние JS-скрипты не требуются.
- [catalog.json](../../../data/requirement-bank/embeddings/received-2026-11-22/catalog.json)
  — наши требования с глобальными ID, эмбеддингами и весами TF-IDF.
- [webgen-train-embeddings.json](../../../data/requirement-bank/embeddings/received-2026-11-22/webgen-train-embeddings.json)
  — тексты целых ТЗ train-части и их эмбеддинги, а не разметка требований.

Каталог `data/` игнорируется Git. Последний файл занимает около 90 МБ; HTML тоже
содержит исходные тексты train. По AGENTS.md сырые данные и большие файлы не
коммитятся. Поэтому после клонирования ветки исходники нужно получить отдельно
и положить по указанному пути. В Git предназначены этот разбор, скрипт аудита,
контрольные суммы и [таблица соседей](neighbors.csv).

## Что проверено

Каталог содержит 217 требований из тех же 15 ТЗ, что и наш
[первый анализ](../report.md). Исходные поля и ID совпадают полностью; изменять
разметку или перенумеровывать требования при переносе не потребовалось.
Train-файл содержит 6 667 ТЗ. В обоих наборах векторы имеют размерность 1 024,
содержат конечные числа и не являются нулевыми. ID точек карт совпадают с JSON.
Подробные числа и происхождение файлов связаны с MLflow run в [run.json](run.json).

В HTML модель обозначена как BGE-M3. Для требований можно переключать BGE-M3 /
TF-IDF и t-SNE / UMAP; цвет показывает явность требования. Для train доступны
две проекции BGE-M3 и 13 подписанных групп. Алгоритм получения групп,
revision модели, параметры кодирования, проекций и seed не приложены.
Поэтому мы сохранили результат, но пока не можем полностью повторить его построение.

Наш прежний TF-IDF использовал символьные n-граммы и TruncatedSVD. Поставляемый
TF-IDF содержит словарные веса, а новая карта использует другие проекции.
Сравнение внешнего вида этих карт не изолирует эффект замены TF-IDF на BGE-M3.

## Что это даёт для банка

Косинус посчитан по исходным векторам требований, а не по расстоянию на картинке.
Для каждого требования сохранены ближайшие соседи из других ТЗ. Колонка TF-IDF
в таблице рассчитана из весов полученного каталога, не из прежнего эксперимента.

| Повторяющийся смысл | Примеры ID | Кандидат в общий шаблон |
| --- | --- | --- |
| Соответствие результатов поиска запросу | webgen-057-R3.1, webgen-096-R2.1 | Результаты соответствуют запросу и заданным фильтрам |
| Отправка сообщения в обсуждение | webgen-058-R4.1, webgen-092-R4.1 | Пользователь отправляет сообщение в выбранное обсуждение |
| Учёт рабочего времени | webgen-082-R4, webgen-084-R6 | Пользователь записывает время для указанного объекта |
| Цвет компонентов | webgen-084-R10, webgen-097-R7 | Компоненты имеют ожидаемый цвет; сам цвет — параметр |

Последняя пара особенно показательна: требования близки, хотя ожидаемые цвета
разные. Они подходят для одного проверяющего шаблона, но не являются одинаковыми
конкретными требованиями. Аналогично нужно сохранять роль пользователя, объект,
условия доступа, отрицания и зависимости.

## Что делать дальше

1. Вручную просмотреть соседей и отметить: одинаковое требование, один шаблон с
   разными параметрами, связанное требование или ложное совпадение.
2. Дополнить банк подтверждёнными шаблонами. У каждого сохранить исходные ID,
   условия применимости, параметры и способ проверки. Тип `code` / `llm`
   определять по проверочному правилу, а не по близости эмбеддингов.
3. При новом ТЗ искать несколько кандидатов в банке, проверять их применимость
   и заполнять параметры из ТЗ. Непокрытые специфичные требования разбирать отдельно.
4. На отложенных ТЗ сравнить TF-IDF, эмбеддинги и их сочетание: долю подходящих
   кандидатов, пропуски требований, лишние требования и стоимость. До этого
   нельзя утверждать, что новый подбор точнее или дешевле.

Группы train можно использовать для выбора разнообразных ТЗ при расширении банка.
Но требования к ним ещё предстоит получить: эмбеддинг целого ТЗ их не заменяет.
ТЗ, использованные для разработки шаблонов, нужно отделить от итоговой проверки
переноса на незнакомые задачи. Наши исходные 15 ТЗ уже участвовали в разработке.

Карта помогает выбирать кандидатов, но не доказывает равенство требований.
Ограничения кластеризации проекций описаны в
[документации UMAP](https://umap-learn.readthedocs.io/en/latest/faq.html#can-i-cluster-the-results-of-umap).
Модель BGE-M3 поддерживает многоязычный поиск и разные длины текстов:
[карточка авторов](https://huggingface.co/BAAI/bge-m3).

## Как повторить аудит

Из корня проекта, после размещения трёх исходников:

```powershell
uv run python scripts/inspect_requirement_embeddings.py --input data/requirement-bank/embeddings/received-2026-11-22 --output data/requirement-bank/embeddings/audit-repeat
```

Аудит проверяет состав файлов и считает соседей без вызовов LLM, загрузки весов
или повторного построения проекций. Запуск требует чистого committed checkout.
