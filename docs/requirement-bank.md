# Расширенный банк требований

Основной файл: [configs/requirement-bank.json](../configs/requirement-bank.json).
Схема: [requirement-bank.schema.json](../configs/requirement-bank.schema.json).

Банк составлен по прежним разборам test и новым разборам train. Формулировки и ссылки
на исходники выбраны ассистентом вручную. TF-IDF использовался для поиска кандидатов,
а не как правило автоматического объединения. API и внешние LLM не вызывались.

Это версия для последующего тестирования. Она не доказывает улучшение качества или снижение стоимости судьи.

## Что находится в карточке

- `id`: постоянный ID шаблона. Это не ID требования конкретного приложения.
- `criterion`: обобщённое требование.
- `applies_when`: когда шаблон можно выбрать по ТЗ.
- `parameters`: какие данные необходимо извлечь из ТЗ; значения здесь описаны, а не заполнены.
- `source_ids`: исходные требования, на которых основан шаблон. Это примеры происхождения, не полный реестр покрытия корпуса.
- `rule`: предлагаемый способ проверки — `code` или `llm`.
- `checker` и `checker_status`: существующая функция или отметка, что её ещё нужно реализовать.
- `instructions`: как проверять требование или какое условие должен реализовать будущий checker.
- `source_notes`: какую часть составного исходного пункта покрывает шаблон.
- `specializes`: более общий шаблон того же действия, если применимо.
- `validation_status: not_evaluated`: качество этого шаблона на приложениях ещё не оценено.

## Что уже исполняется

`ui.background_color` и `ui.component_color` используют функции из
[requirement_templates.py](../src/decomp_judge/requirement_templates.py).
Они сравнивают заданный HEX с уже собранными вычисленными RGB-цветами. Для компонентов
используется та же операция сравнения, что и для фона, но другая область наблюдения.
Выбор области и сбор CSS не автоматизируются этими функциями. Это не готовая проверка всего оформления.

`implemented` означает наличие функции с модульными тестами, а не подтверждённое качество на приложениях.
`planned` означает, что детерминированная проверка описана, но функции ещё нет. Поле checker у неё отсутствует.
Такие правила пока нельзя исполнять как code. Автоматического переключения на LLM эта отметка не добавляет.
Для `llm` есть инструкция; она ещё не проверена в эксперименте с расширенным банком.

## Как использовать при декомпозиции

1. Найти подходящие шаблоны по ТЗ и проверить `applies_when`.
2. Подставить объект, роль, поля, цвет и другие параметры из ТЗ. Незаполненный параметр не заменять выдуманным значением.
3. Если текст неоднозначен, явно записать трактовку. Неявные требования включать только по принятой политике разбора.
4. Сохранить исходные связи и зависимости. Не добавлять вход, оплату, серверную БД или ограничения времени только потому, что они часто встречаются.
5. Для одного действия выбирать предметный вариант вместо дублирования общего: например, создание заказа вместо двух независимых проверок «создать объект» и «создать заказ».
6. Составной пункт можно проверять несколькими частями, но итог сопоставлять с исходным requirement_id. Альтернативы «изменить или отменить» не превращать в требование обоих действий.
7. Специфичные пункты, которым нет подходящего шаблона, сохранить отдельно. Отсутствие записи в source_ids не означает, что шаблон неприменим.

Автоматический подбор шаблонов, заполнение параметров и подключение банка к судье — следующий этап.
Сейчас сформированы сами карточки и проверена их структура.

## Общие правила оценки

Сначала использовать доступные функциональные свидетельства; если их недостаточно, продолжать
проверку по коду по правилам двухэтапного судьи. Доступность кнопки не подтверждает выполнение операции.
Невозможность подготовить данные или роль сама по себе не доказывает FAIL данного требования.
Доказанную ошибку операции не скрывать успешным наличием её исходников.
Свидетельство должно указывать, что наблюдалось или какой код изучен.

Возвращаемый функциями цветов UNRESOLVED — промежуточный сигнал об отсутствии достаточных наблюдений,
а не новый итоговый вердикт судьи. Он не заменяет предусмотренную дальнейшую проверку.

## Проверка структуры

Из корня проекта:

```powershell
uv run python -m decomp_judge.requirement_templates
make check
```

Проверяются уникальность ID, наличие исходных требований, согласованность MD/JSON,
статусы checker, корректность source_notes и отсутствие циклов специализации.
Для повторения нужны производные аннотации из data/requirements и соответствующие Markdown.
Сырые train/test JSONL, модель и ключ для этого не нужны.
