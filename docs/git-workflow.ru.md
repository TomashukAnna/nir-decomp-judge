# Правила работы с git и GitHub

Короткая выжимка для студента НИР при проекте mas-science: что делать в первый день, как устроен
цикл одной задачи и что именно проверяется на ревью. Полные памятки лаборатории с обоснованиями
перечислены [в конце](#где-читать-подробно); при расхождении верьте им и скажите руководителю.

## Зачем эти правила

Правила не про аккуратность ради аккуратности. У каждого есть причина, и её полезно знать: тогда
понятно, как поступить в случае, который здесь не описан.

| Правило | Зачем оно |
|---|---|
| Вся работа через pull request | PR это запись того, что сделано и почему. По ним идут ревью и контрольные точки; того, чего нет в PR, для оценки не существует |
| Небольшие ветки, push каждую рабочую сессию | Маленький дифф проверяется за минуты, большой откладывается на неделю. По истории видно, что работа шла равномерно, а не за ночь до встречи |
| Имена веток и PR по списку типов | История `main` читается как оглавление работы. Проверяет CI, спорить не о чем |
| Plan пишется руками и не правится, Done по диффу | План показывает замысел до работы, итог показывает, что вышло. Расхождение между ними и есть содержание ревью |
| Правки по ревью отдельными коммитами, без force-push | Ревьюер видит, что изменилось с прошлого прохода. Force-push отвязывает комментарии от строк |
| Один `make check` перед коммитом, в CI и у ассистента | Проверка везде одна и та же, поэтому «у меня работало» не бывает |
| Секреты, данные и веса вне репозитория | Историю git нельзя почистить задним числом: ключ, попавший в коммит, скомпрометирован навсегда, а большой файл навсегда утяжеляет клон |
| Эксперимент это issue плюс запуск MLflow | Каждое число в отчёте прослеживается до коммита, конфига и seed. Число без запуска нельзя ни проверить, ни защитить |
| Решения в `docs/adr/` | Через три месяца вы сами не вспомните, почему выбрали этот бейзлайн. На защите об этом спросят |

## В первый день

1. Создайте репозиторий из шаблона в **личном** аккаунте (шаги в README, раздел «Первый запуск»).
2. Видимость выбираете вы. Рекомендуем публичный, если этому не мешают данные:

   | Что обеспечивает GitHub сам | Публичный | Приватный |
   |---|---|---|
   | Защита `main`: только через PR, с аппрувом и зелёными проверками | да | нет |
   | Автоматический запрос ревью по `CODEOWNERS` | да | нет |
   | Поиск секретов при push | да | нет |

   В приватном репозитории правила те же, но держатся на договорённости: единственный
   автоматический барьер там CI.
3. Добавьте руководителя collaborator'ом с правом Write: Settings → Collaborators → `AnatolyPershinov`.
4. Клонируйте с `--recurse-submodules`, выполните `uvx pre-commit install` и убедитесь, что
   `make check` проходит. `pre-commit install` нужен в каждом новом клоне.
5. В публичном репозитории включите защиту `main` (Settings → Rules → Rulesets): обязательный PR,
   один аппрув, закрытые обсуждения, проверки `check`, `hygiene`, `conventions`.
6. Заведите второй remote на другом хостинге и пушьте туда тоже: доступ к GitHub бывает нестабильным.

## Цикл одной задачи

1. **Issue.** Для эксперимента по форме Experiment: гипотеза, постановка, ожидаемый результат.
   Пустые issue отключены намеренно.
2. **Ветка** от свежего `main`: `<тип>/<короткое-описание>`. Одна ветка на одно изменение,
   живёт дни, а не недели.
3. **Коммиты** небольшие. В конце каждой рабочей сессии коммит и push: по истории должно быть
   видно, что работа шла равномерно, неделя за неделей.
4. **Draft PR открывайте сразу**, с первого push. Раздел «Plan» пишете сами, три-пять строк о том,
   что собираетесь сделать. После открытия Plan не правится.
5. **Перед снятием Draft**: `make check` и `uv lock --check` проходят; заполнены «Done» и
   «How to reproduce»; стоит `Closes #N`; assignee вы, reviewer руководитель (в приватном
   репозитории назначьте его вручную).
6. **Ревью.** Руководитель оставляет все замечания за один проход. Вы правите **отдельными
   коммитами**, без squash, rebase и force-push, и под каждым обсуждением отвечаете, что изменили
   и в каком коммите. Затем Re-request review. Обсуждения закрывает руководитель, не автор.
7. **Мерж** после аппрува и зелёного CI: squash and merge. Заголовок PR станет сообщением коммита
   в `main`, поэтому он пишется по тем же правилам, что и коммит.

Пока ждёте ревью, начинайте следующую ветку от текущей. Не копите работу семестра в одном PR.

## Имена и формат

| Что | Правило | Пример |
|---|---|---|
| Типы | `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `exp` | `exp` для серии экспериментов |
| Ветка | `<тип>/<описание>`: строчные латинские буквы, цифры, `.`, `_`, `-` | `feat/interpretation-sampler` |
| Заголовок PR | `<тип>: описание`, тот же тип, что у ветки | `feat: add interpretation sampler` |
| Тема коммита | повелительное наклонение, до 50 символов, без точки | `fix: handle empty spec` |
| Тело коммита | что изменилось и зачем; строки до 72 символов | |
| Язык | код, имена, коммиты и заголовки PR на английском; документы на вашем языке | |

Имя ветки и заголовок PR проверяет CI регулярными выражениями: `^(типы)/[a-z0-9._-]+$` и
`^(типы)(\(область\))?!?: .+`. Сообщения вида `fix`, `changes`, `WIP`, `finally works` ничего не
говорят ни руководителю сейчас, ни вам через три месяца.

## Что нельзя

- Коммитить `.env`, ключи и токены. Ключ, попавший в историю, скомпрометирован: сначала отзовите
  его и выпустите новый, затем решите с руководителем, переписывать ли историю.
- Коммитить сырые данные, веса моделей, логи, `mlruns/`, файлы больше 10 МБ. Данные хранятся вне
  репозитория, в README написано, как их получить.
- Коммитить с `--no-verify`. Если проверка упала, устраняется причина.
- Переписывать запушенную историю `main`, делать force-push в ветку с открытым PR.
- Править `main` напрямую. Исключение только по договорённости с руководителем.
- Править раздел Plan после открытия PR и закрывать обсуждения ревью самому.

## Что проверяет CI на каждом PR

| Задание | Что делает |
|---|---|
| `check` | `uv sync --locked`, затем `make check`: ruff, mypy, pytest |
| `hygiene` | gitleaks по рабочему дереву, приватные ключи, большие файлы, корректность yaml и toml |
| `conventions` | имя ветки и заголовок PR по списку типов |

Тот же `make check` запускается pre-commit'ом на вашей машине и хуком LLM-ассистента.
`uv.lock` коммитится; после изменения зависимостей выполните `uv lock`.

## Эксперименты и решения

- Каждый эксперимент это issue и запуск в MLflow. Запускайте скриптом из рабочей копии и только
  после коммита, тогда MLflow сам запишет коммит. Теги: `stage`, `dataset`, `model_family`, `pr`.
- Строка таблицы результатов: коммит, путь к конфигу, seed, id запуска, метрики. Числа без
  названного запуска на ревью не принимаются.
- Решения о структуре, инструментах, данных, метрике, бейзлайне записываются в
  `docs/adr/NNNN-название.md` по шаблону `0000-template.md`: создаются в ветке со статусом
  proposed, принимаются в том же PR. Принятую запись не правят, её заменяет новая.

## LLM-ассистенты

- Инструкции для ассистентов: `AGENTS.md` и общие правила лаборатории в `.agents/overlay`.
  Подключены Claude Code и Codex: у каждого свой слой (`.claude/`, `.codex/`), skills и хук
  `make check` одни и те же. В Codex один раз подтвердите доверие проекту, иначе `.codex/` не
  загрузится.
- Раздел Plan пишете вы сами. Раздел Done ассистент составляет по диффу, вы проверяете.
- Ассистент не снимает Draft, не закрывает обсуждения и не мержит.
- За код, написанный с ассистентом, отвечаете вы: на ревью вопрос «почему так» задаётся вам.
- Первый проход ревью в этом проекте может делать ИИ-ассистент руководителя. Решение об аппруве
  принимает руководитель.

## Что показать к контрольной точке

1. Репозиторий запускается из чистого клона командами из README.
2. PR, смерженные за период, с заполненными Plan, Done и How to reproduce.
3. Записи в `docs/adr/` по принятым решениям.
4. Запуски MLflow на коммитах этих PR с обязательными тегами.
5. Зелёный CI на `main`; в истории нет секретов и данных.
