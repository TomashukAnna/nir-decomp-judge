# Разбор 15 ТЗ WebGen-Bench

Статус: разбор завершен, 217 требований оформлены в Markdown и JSON. Источник ТЗ — поля `id` и `instruction` локального `test.jsonl` WebGen-Bench.

Все 15 ТЗ рассматриваются на равных и входят в единую сводку.

Номера задач — индексы строк с нуля. Полный список: 11, 12, 16, 26, 28, 47, 49, 57, 58, 72, 82, 84, 92, 96, 97. ID WebGen-Bench на единицу больше: например, № 26 — `000027`.

## Файлы и формат

На каждую задачу — `<номер>.md` здесь и `data/requirements/<номер>.json`. Markdown содержит ТЗ и таблицу ручного разбора. JSON содержит `task_index`, `webgen_id`, `query` (исходное ТЗ) и заполненный список `requirements`. Команда `scaffold` создаёт новые заготовки с пустыми таблицами; существующие разборы она не изменяет.

Каждое требование содержит все поля:

| Поле | Значение |
|---|---|
| `requirement_id` | Непустая строка, например `R1` или `R1.1`; уникальна внутри задачи |
| `criteria` | Проверяемая формулировка требования |
| `source` | Цитата из ТЗ, на которой основано требование; для неявного — цитата, из которой оно выводится |
| `kind` | `explicit` (явное) или `implicit` (неявное) |
| `rule` | `code` или `llm`|
| `parent` | ID родительского требования либо `null` для корневого |
| `prerequisites` | Список ID необходимых требований этой задачи либо `[]` |

Спорное прочтение и выбранная трактовка записываются в Markdown. Не включать в требования условия проверки, которых нет в ТЗ.

Схема — `configs/requirements.schema.json`, модель и скрипт — `src/decomp_judge/requirements_bank.py`. `make check` проверяет схему, обязательные поля, значения, уникальность ID, ссылки и отсутствие циклов отдельно в иерархии и зависимостях. Также проверяются комплект из 15 пар, заполненность JSON и совпадение ТЗ и требований в Markdown и JSON. Смысловая обоснованность требований проверяется вручную.

## Команды из корня проекта

Создание в новой папке или чистом checkout без этих 30 файлов:

```powershell
uv run python -m decomp_judge.requirements_bank scaffold --source '../data WebGen-Bench/test.jsonl'
```

Скрипт не перезаписывает существующие разборы. Он не использует модель или сеть.

После правок Markdown обновить JSON и проверить согласованность:

```powershell
uv run python -m decomp_judge.requirements_bank export
uv run python -m decomp_judge.requirements_bank check --require-complete
```

Экспорт читает таблицы Markdown и обновляет JSON после проверки всех задач. Последняя команда отклоняет незаполненную задачу или расхождение с Markdown. Этот режим уже включён в `make check`.

## Трудности и ограничения разбора

В ТЗ не всегда понятно, что именно нужно реализовать. Например, слова «управление» и «анализ» не задают конкретные действия. При разборе я выбирала трактовку и записывала ее в заметках. Важно было не добавить собственные пожелания к приложению.

Также было сложно выбрать детализацию: оставить одну общую формулировку или разделить ее на несколько требований. Я не стала добавлять требования только ради ориентира 15–20. При этом подсчет родителей вместе с дочерними требованиями может увеличивать вес одной функции в оценке.

Метка `code` означает, что требование можно проверять детерминированно. Но такую проверку еще нужно написать и убедиться, что она работает правильно. Даже если код поможет написать LLM, его нужно проверить: в нем тоже могут быть ошибки. Создание проверки может оказаться сложнее и дороже, чем один запрос к LLM-судье. Поэтому нужно отдельно учитывать затраты на разработку проверки и на ее повторные запуски. Пока метки `code` и `llm` не показывают, какой вариант будет дешевле и надежнее на практике.
