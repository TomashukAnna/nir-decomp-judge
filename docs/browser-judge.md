# Проверка запуска и исходников

[Передача задач 26 и 39 для запуска на внутреннем API](browser-judge-handoff.md).

Судья получает ТЗ, список требований, исходное приложение и отдельную рабочую копию с установленными зависимостями. Подготовьте чистую рабочую копию кода судьи и переменную LITELLM_API_KEY для лабораторного API.

```powershell
uv run --with playwright==1.52.0 python -m decomp_judge.browser_judge `
  --app PATH_TO_SOURCE --runtime-app PATH_TO_RUNTIME_COPY `
  --spec PATH_TO_SPEC --requirements PATH_TO_REQUIREMENTS_JSON `
  --opencode PATH_TO_OPENCODE --output PATH_TO_NEW_OUTPUT
```

Сейчас распознаются сценарий dev на Vite, команды запуска Python в README без аргументов и точки входа Python в корне приложения или src. При неопределённой команде все требования передаются судье по исходникам. Для установленного Edge можно добавить --channel msedge.

На функциональном этапе модель получает наблюдения запуска и выбирает действия. Для веб-приложения доступен Playwright. Для Python доступны чтение локальных файлов для планирования и вызовы публичных функций с аргументами JSON. Функциональные PASS и FAIL требуют ссылки на наблюдение. Остальные требования передаются OpenCode одним пакетом. Отчёт содержит источник решения и причину перехода к исходникам.

Веб-этап не читает исходники: модель получает видимые элементы управления с ID, именами и подписями, использует действия Playwright и может запросить вычисленный CSS через `styles`. Чтение кода остаётся отдельным этапом. В Python-режиме чтение разрешено для планирования независимых вызовов функций; само по себе оно не обосновывает функциональный PASS/FAIL.

Лимит выполнения — `FUNCTIONAL_MAX_ACTIONS` (по умолчанию 20); для Python разрешено до `FUNCTIONAL_MAX_SOURCE_READS` чтений (по умолчанию 3). Ошибки JSON и свидетельств передаются модели с диагностикой: до трёх исправлений после первого ошибочного ответа, отдельно от лимита действий. Уже принятые вердикты сохраняются, если другая строка ответа нарушает схему. Требования без принятого вердикта становятся UNRESOLVED и уходят в код. Модель не обязана получать PASS: достаточных наблюдений для решения может не быть.

Последний этап OpenCode также использует цикл до трёх исправлений из PR #11; ранее он отсутствовал в этой ветке, основанной на более раннем main. Новые ошибки не исправляются удалением полей: модель получает диагностику строгого валидатора и возвращает полный исправленный JSON в той же сессии.

Сохраняются `response-N.txt`, `response-N-usage.json` с причиной завершения и токенами, `observations.json` с ошибками и наблюдениями, `functional-session.json` с числом действий, исправлений и неоценёнными ID. Пустой ответ или исчерпание бюджета не превращаются в FAIL приложения. Диагностика финального списка указывает ID проблемного требования; успешные пробы и ошибки запуска различаются при проверке свидетельств.

Проверки без ключа входят в `make check`. Необязательный локальный тест настоящего Edge:

```powershell
$env:RUN_BROWSER_SMOKE = '1'
uv run --with playwright==1.52.0 pytest tests/test_browser_judge.py
```

Этот тест проверяет получение элементов страницы, заполнение поля и вычисленный цвет без LLM. Он не заменяет повторный прогон задач с моделью.

Запускайте доверенные приложения в изолированной среде. Отдельная копия и сокращённое окружение процесса не заменяют системную изоляцию. Журналы действий и наблюдения сохраняются локально, итог функционального этапа и счётчики токенов записываются в MLflow.
